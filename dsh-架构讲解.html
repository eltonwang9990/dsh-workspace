0一句话定位

先记住三句话，后面所有细节都是它们的展开。

三个根本论断 ① 一切能力都是插件  ·  ② 一切装配都是配置层叠加  ·  ③ 全局状态归宿主，会话状态归 preset

DSH 不是「一个聊天程序」，而是把 插件（能力） 交给 配置（装配） 去组合出来的一台运行时代理。你看到的模型、工具、界面、沙箱，没有一样是硬编码的——它们全是插件的实例，靠配置树拼装而成。

1三层结构

从外到内，越往里越「通用」，越往外越「具体」。

CLI dsh 命令层极薄入口：解析自身 flag → 选中 profile → 加载对应 runner。它不理解任何业务。
Profile 层（运行模式）web / headless / 自定义。本质是一组 bundle 的 patch 逐层叠加 + 用户覆盖。
内核 Cordis 运行时service / event / plugin / scope / realm。配置树在这里被实例化成插件树。

关键：CLI 只做「转发」

CLI 只解析自己认识的 flag，遇到第一个不认识的 token 就停手，把后面全部原样交给 profile。所以 dsh --profile web --port 8080 里的 --port 不是 CLI 的，而是 web 应用的。

关键：Profile 是「装配清单」，不是代码

一个 profile 目录里放 dsh.profile（按顺序列 bundles）、cordis.patch.yml（用户覆盖层）、package.json（树外插件依赖）。它决定「要装哪些部件、按什么顺序、用哪些参数」——而部件本身（插件）是独立于 profile 存在的。

2配置叠加模型

这是整套系统可扩展性的根源：改行为，靠「盖章」而不是改代码。

配置树从空根开始，每一层 patch 像贴纸一样盖上去。顺序决定优先级：先解析的在下层打底，后解析的在上层覆盖。最后贴的最强。

  1. dsh.profile.bundles 里每个 bundle 的 patch（按列表顺序）
  2. profile 自己的 cordis.patch.yml
  3. home 级的 $DSH_HOME/cordis.patch.yml
  4. --patch 命令行覆盖（最外层，最后赢）
这个设计的价值 部署方、用户、单次命令行三者都能在不改任何代码的前提下改写行为，且各自的作用域清晰：越靠外的层越「临时」、越「个人」。

配套有两个只读检查命令：--dump-default-config（看默认组合）和 --dump-config（看最终组合），启动前就能核对配置树长什么样。

3两个平面：全图最关键的一笔

每个能力该放哪，只有两个答案。判断标准不是「功能大小」，而是「所有权」。

Host 平面（宿主组合） Agent preset 平面（会话组合）
生命周期：进程级，一启动就存在 生命周期：每个会话挂载
装什么：注册表、持久化、沙箱/审批栈、模型路由 装什么：工具、人设、prompt 段落
为什么：它们是单例，被所有会话共享，preset 不该拥有 为什么：它们是每个会话自己的东西，只有 preset 该拥有

判定铁律：一个能力放哪里，看它是「注册表」还是「工具」

规则可以压缩成一句话——凡是服务/注册表级 → host；凡是只有这个 agent 会调用的模型工具 → preset。具体落到三条判据：

  • 会被跨会话查询：tools、subagents 注册表要经 api-proxy 暴露给浏览器读取 → 必须 host 单例。
  • 进程中只能注册一次：一个 provider 名字全局唯一，重复注册会抛错 → 必须 host 单例。
  • 在会话诞生前就必须解析：preset 的 inject 在会话存在前无法解析依赖 → 必须 host 单例。

反过来，像 tool-bash、tool-fs、tool-web、tool-todo 这些行，自己不提供任何东西，只是往宿主注册表里登记一个名字——它们天然属于 preset。

第三类：isolate realm（隔离领域）

当某个服务既不是宿主单例、又必须被同组多个行共享、且不能被别的 preset 看到时，用 isolate: {某服务: true} 框成一个「preset 私有的领域实例」。

4Host 与 Client：两个执行环境

一个进程在 Node 里，一个在浏览器里，中间只有一条受控的 JSON 通道。

环境跑在哪负责什么
HostNode.js 进程文件、网络、命令、模型路由、沙箱、审批、持久化
Client浏览器页面主题、布局、页面状态、工具卡片、Slot UI

二者通信是单向受控的：只有 host.call(method, args) 从 Client 调到 Host，且只允许无损 JSON跨越。Host 不能反向推给 Client 任意结构。

两个横切的守护层

  • 审批栈（approval stack）：环绕在需要审批的操作外面。危险写文件、越权命令要先过 answerer；没有 answerer 就 fail-closed（失败即拒）。
  • 沙箱（sandbox）：文件策略的真正执行者。本会话是 workspace-write 模式——只能写 workspace 根目录，越界需单独升级授权。

这两层都属于 host 平面，因为它们要守护的是所有会话，而不是某一个 agent。

5会话与持久化

会话的生命周期、存储、查询、压缩，全部围绕「按工作目录分组」这一事实。

  • 存储分区：会话按 workspace 根目录分组存储，路径是 ~/.dsh/sessions/<工作目录转义>/<session-id>。路径里的中文会被转义成 ~xxxx~ 形式。
  • 持久化链：session-persistence → jsonl 落盘 → session-query（sqlite）做查询 → projection-cache 加速投影。
  • 遥测：session-telemetry 走 OpenTelemetry（otel），导出日志/指标/追踪。

这些全是 host 单例——因为它们是跨会话共享的服务，一个实例服务所有会话。

压缩（compaction）——一个 preset 选择

上下文超限时折叠历史：tool-result-pruner 按 threshold / head / tail 裁剪超长工具结果。「要不要压缩」是每个 agent 的选择，所以它在 preset 层；但 token-meter（计账器）留在 host，见上一章的反面案例。

6代理与委托：代理的代理

都建立在 host 的 subagents 注册表单例之上，但形态不同。

机制语义记忆模型
subagent普通委托（独立上下文）每次独立，不共享对话
fork分叉：继承父会话上下文复制已完成对话，继续
workflowJS 编排脚本把活扇形铺到大量子代理带 phases / pipeline / 屏障
ralph每轮开全新无记忆子代理循环用共享 workspace 做长期记忆

一个精确的归属区分：subagents 注册表和它的 spawn/fork 后端在 host（进程单例、被跨会话查询）；但 workflows 引擎在 preset 私有的 realm——因为「没有任何 agent 之外的东西读它」，放私有领域反而更干净。

7动态插件：运行时临时扩展

不属于仓库源码，重启即消失。它用「不可变版本」解决「进化 vs 回滚」的老难题。

Plugin（pluginId） —— 可跨版本演进的「插件实体」 └─ Package（packageId）—— 每次改动 = 追加一个不可变源代码快照 └─ Run（pluginRunId）—— 一次激活尝试，连着审批 / 加载 / 报错

四条设计保证

  • 代码不可变：改代码 = 追加新 Package，永不覆盖旧版本 → 天然可回滚。
  • 副作用可逆：所有 service / timer / handler 都挂在当前 Fiber 上，stop / update / undefine 能干净拆除。
  • 审批分级：单勾只授权当前 Package；双勾授权该插件未来所有版本。
  • 更新语义：update 会先停旧 Run 再启新 Package；失败不会自动回滚旧版，需显式 rollback。

9设计哲学：三条分离

把整张地图收束成三对「分离」，它们是所有取舍背后的同一只手。

分离解决什么落在哪
全局 vs 会话单例不会被某个会话污染，会话状态不污染全局host plane vs preset plane
装配 vs 代码改行为不改代码，改代码不动装配patch 层 vs 插件
进化 vs 覆盖版本演进永不破坏既有运行实例不可变 Package + 追加版本
一句话收尾 DSH 之所以既能让部署方统一掌控、又能让每个会话甚至运行时动态地临时扩展而互不污染，靠的就是这三对分离。看懂它们，就看懂了整张地图。
